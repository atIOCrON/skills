# Implementation Readiness

Before dispatch, map every owned acceptance group to its candidate mechanism,
runtime owner and local/inherited/external evidence. Distinguish introduced or
modified lifecycle implementation from routing, selection, configuration or
reachability of an unchanged dependency lifecycle; changed outcomes alone do not
establish local lifecycle ownership.

Inventory touched-surface checks, prerequisites (locked dependencies, services,
fixtures, disabled components) and target-branch CI. Select every applicable
capability skill; require it to define fast authoring, exact-candidate and final
integration checks, source/effective representations, immutable input identities
and equivalence rules. Reuse must cover every determining input: source,
configuration, dependencies/fixtures, toolchain, runtime binding and effective
result. Missing identity means rerun. Record commands/evidence without copying
ecosystem procedures into orchestration.

Copy review-required external source/effective files or sufficient pinned excerpts
into the neutral pack: paths, hashes and replay logs alone do not supply content.
Prepare reproducible local checks where CI cannot run. Resolve missing required
agent gates and ownership before implementation without silently adding unrelated
CI/tooling. Record intended commands, agreed gaps, and each human/external check's
procedure, owner, prerequisite and pending result separately.

Candidate-owned runtime lifecycle changes need executable behavioral proof at
the highest practical local seam; source-shape assertions only supplement it.
Unchanged dependency-owned behavior may rely on exact effective-code/runtime
binding identity, applicable inherited tests and separate external acceptance.
Lightweight doubles may prove routing/binding; fake provider/server/persistence/
account/order state transitions do not prove unchanged production lifecycles.
